# 电商问数 Agent 评测证据化设计

## 目标

在不扩大数据库数据规模的前提下，把现有回归评测、Trace 和 API 压测改造成可复现、可比较、可追溯的证据链，使简历中的准确率、延迟、并行收益、缓存命中率和稳定性结论都能反向定位到原始 JSON 与 Trace。

## 范围边界

- 本阶段评估 Agent 的语义正确性、链路性能和接口稳定性，不宣称大数据量下的 MySQL 性能收益。
- 不使用不同模型、不同 Prompt 或不同测试集之间的结果计算性能提升。
- SQL 字符串片段仅作为兼容性诊断，不再作为普通问数的首要正确性指标。
- 缓存分别记录关闭、冷缓存和暖缓存，精确重复请求只用于观察上限，不作为简历主结论。
- 安全拦截、澄清、Grounding 和普通问数分别统计，避免简单分支抬高整体准确率。

## 评测集设计

评测集最终目标为 40 个独立业务意图、120 条自然语言表达。每个意图包含 3 种表达，但宏平均按意图计算，避免近义改写重复抬高分数。

开发集包含 30 个意图、90 条表达；隔离测试集包含 10 个意图、30 条表达。切分以 `intent_id` 为单位，同一意图的不同表达不得跨集合。

普通问数 Case 使用 `gold_sql` 作为可执行真值；安全、澄清和 Grounding Case 使用确定性的预期分支与错误类型。每条 Case 记录 `category`、`intent_id`、`paraphrase_id`、`ordered_result` 和允许的数值误差。

## 正确性指标

普通问数执行 Agent SQL 与 Gold SQL，并对结果进行规范化比较：

- 列名统一为小写，数值按容差比较，日期和 Decimal 转换为稳定表示。
- 非排序问题忽略行顺序；Top、排名和显式排序问题保留顺序。
- 同时报告 Execution Accuracy、SQL 生成率和 SQL 执行成功率。
- 按 `category` 和 `intent_id` 输出分层结果及宏平均。

分支指标独立计算：

- Grounding：完全未命中、部分命中、匹配值和缺失值是否符合预期。
- 安全：拦截召回率与正常查询误拦截率。
- 澄清：应澄清问题的召回率，以及明确问题被错误澄清的比例。

## Trace 证据

每条 Trace 在请求级记录实验元数据，包括运行 ID、Case ID、意图 ID、数据集哈希、模型、Prompt 哈希、缓存模式和代码版本。每个节点继续记录开始时间、结束时间、耗时、错误和缓存统计。

三路召回收益按 Trace 计算：

```text
串行估算耗时 = recall_column + recall_metric + recall_value 的耗时总和
并行墙钟耗时 = 三路最晚结束时间 - 最早开始时间
估算节省耗时 = 串行估算耗时 - 并行墙钟耗时
估算节省比例 = 估算节省耗时 / 串行估算耗时
```

报告必须记录可计算 Case 数、缺失节点 Case 数、平均值和 P50/P90/P95，不能只保留最终百分比。

## 缓存实验

Embedding 与关键词扩展缓存提供启停、清空、累计统计和请求级增量统计。缓存模式包括：

- `disabled`：完全绕过读写缓存。
- `cold`：启用缓存但运行前清空。
- `warm`：在相同模型和测试集上保留前序运行缓存。

比较报告仅在模型、Prompt 哈希、Case 哈希和关键运行参数一致时计算 Delta；不一致时明确拒绝比较。

## API 稳定性

API Benchmark 使用固定 Case 分布，区分正常成功、预期业务分支和技术错误。报告保存每个请求的耗时、HTTP 状态、最终 SSE 事件、错误类型、Trace 路径，并汇总吞吐量、P50/P90/P95/P99 和技术错误率。

## 产物与结论

运行产物按 `eval/reports/<run_id>/` 隔离，至少包含评测结果、Trace 汇总、API 压测和 A/B 对比。简历结论必须引用运行 ID，并能从汇总指标回溯到 Case 和 Trace。

允许形成的结论示例：

```text
在相同模型、Prompt 和 120 条测试表达上，Execution Accuracy 从 A 提升到 B；
三路召回并行相较串行估算平均减少 X ms（Y%）；
暖缓存命中率为 H%，平均延迟和 P95 分别下降 M% 与 N%；
在 10 并发、R 次混合请求下，技术错误率为 E%，P95 为 P ms。
```
